So SCCH is the modern managed-code rewrite/wrapper of MVComms, sitting on the MOVA Tools (Windows) side. The native C source ancestor of it is right here in MVComms/; the C# DLL itself ships from a different repository.

The wire protocol SCCH speaks (the bit that pushes detection)
From Chameleon-2-Repo-main/modules/MOVA/source/M8.0/source/MsgTypes.h:

Plain Text

length_lsb, length_msb,          (2 bytes)SOM=0x02, type, retaddr_lsb,     (3 bytes)retaddr_msb, count,              (2 bytes)payload...,checksum_lsb, checksum_msb       (2 bytes)
Six message types (Chameleon-2-Repo-main/modules/MOVA/source/M8.0/source/MsgTypes.h#L24):

ID	Name	Direction	Purpose
0	PING	both	Keepalive
1	UPDATE	both	Per-scan cycle (see below)
2	HANDSHAKE	request/reply	{junctionID}
3	INITIALISE	sim → MOVA	{date, time} — start-of-run
4	EVENT	MOVA → sim	{type, id, description[256]} — log line
5	TERMINATE	sim → MOVA	Stop
The UPDATE message is what pushes detection. It's a paired exchange that runs every scan (Chameleon-2-Repo-main/modules/MOVA/source/M8.0/source/MsgTypes.h#L73):

Sim → MOVA — MsgUpdateRequest:

Plain Text

{  MVByte controllerReady;                         // CRB  IOPort detectors[xg_DETECTOR_PORTS_MAX];        // ← Sim writes detector bits here  IOPort confirms[xg_CONFIRM_PORTS_MAX];          // stage/phase confirms}
MOVA → Sim — MsgUpdateReply:

Plain Text

{  MVBool takeOver;  IOPort forces[xg_FORCE_PORTS_MAX];              // stage demands  IOPort isHoldSignalOn;  IOPort isReleaseSignalOn;  IOPort scOutputChannels[NumberofOutputChans];   // SR/PR}
So MOVA Tools Sim plays the role of the signal controller (lamp/detector hardware) and the Chameleon plays the role of MOVA. Sim pushes detector port states each cycle, MOVA responds with force/hold/release outputs.

Transport
MVComms supports both TCP and RS232 serial, chosen at runtime (Chameleon-2-Repo-main/modules/MOVA/source/M8.0/source/MVComms/clicomms.c#L69). ClientComms_OpenTCP(ipEndPoint, ...) / ClientComms_OpenSerial(commPort, baud, ...) — the same Message_Pack* payloads go down either pipe.

The Chameleon's normal in-field setup is COMMS_TYPE_SERIAL (SCN cable to the controller). For sim/lab use, MOVA Tools Sim opens a TCP socket to the Chameleon and substitutes itself for the controller.

This is also why this protocol is completely separate from AML/55001: AML is a monitoring/configuration API for the operator UI; MVComms is the closed-loop I/O channel that runs MOVA's scan cycle. They don't share a port, framing, or state.

How you'd rebuild SCCH if you needed to
If the MOVA Tools / SCCH source isn't reachable, the recipe is:

Wire layer: re-implement the framing in Chameleon-2-Repo-main/modules/MOVA/source/M8.0/source/Messages.c (length, SOM, type, retaddr, count, checksum) — every function you need is in this repo.
Transport: pick TCP or serial. TCPClient.c/Serial.c are reference implementations you can mirror in C# (TcpClient / SerialPort are the .NET equivalents).
Per-cycle loop: open → HANDSHAKE → INITIALISE → loop { send UPDATE-request with detectors; read UPDATE-reply forces } → TERMINATE.
Match the IOPort sizes: xg_DETECTOR_PORTS_MAX, xg_CONFIRM_PORTS_MAX, xg_FORCE_PORTS_MAX, NumberofOutputChans are in kernel/defines.h and must agree with what the Chameleon expects, otherwise the checksum check passes but field offsets are wrong.
The original SCCH is almost certainly a thin C# port of clicomms.c plus a C# struct mirror of MsgTypes.h.
